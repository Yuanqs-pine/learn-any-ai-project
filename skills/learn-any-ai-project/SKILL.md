# AI 项目通用学习技能

把「系统学习一个新 AI 项目」变成一条可复用的流水线：**画像 → 推导章节 → 生成计划文档 → 用户评审 → 逐章学习 → 状态双向同步**。本技能是「方法论引擎」，不是任何项目的教材；每个项目的知识点与代码都以**该项目目录内的实际文件**为准，技能内部不携带任何项目内容。

## 1. 核心设计原则（为什么能通用、能共享）

| 原则 | 含义 |
|---|---|
| 零项目依赖 | 技能内容不含任何具体项目（路径/文件名/工具栈/技术商标），换任何项目、给任何人用都成立 |
| 内容定制、形式统一 | 只锁「文档外形与写作规范」；**章节数量、主题、顺序由项目画像推导**，绝不复用其他项目的章节 |
| 第一性原理 | 不按"常见模板"猜章节，先问"要理解这个系统，必须走通哪些闭环（环）"，由环推导章 |
| 状态单一事实源 | 目标项目根下的 `.engine/state.json` 是唯一账本；文档中的状态卡、进度总表都只是它的投影 |
| 轻量自包含 | 全部机制（版式规范 + 账本 + 同步规则）定义在本文件内，运行时不需要额外脚本，Agent 按规则直接执行 |
| 学习即产出 | 学完的产物（代码/环境/文档）留在目标项目里就是可交付资产，不产生游离在学习区之外的"教学垃圾" |
| 手动优先、练手≥演示 | 学习目标是让学习者能独立交付：凡能练手的动作（起服务/装依赖/执行命令/解读 log/排错/复现），执行权优先移交用户亲手完成；Agent 负责讲解、给命令、绿条自证与兜底，绝不因"自动更快"而包办 |
| 内容零版本、零废话 | 生成的文档/文件/代码只写一遍且默认即大白话叙述：禁止出现「XX版」字样（如"大白话版/正式版/通俗版"）；括号内只放重点备注（为什么/工程取舍/类比/判读要点）；删除一切废话与冗余 |
| 产物精简与干净 | 交付物（文档/代码/环境）只留必要：文档重点突出、可取舍可复用（§12.2-8）；代码最小够用（§12.1）；临时/中间/调试文件用毕即清、不入账本不进文档（§9.1） |
| 语言跟随用户 | 技能本身不预设语言：学习对话与全部产物（LEARN.md/文档/代码注释）的语言在 S0 与用户确认（默认跟随用户当前使用的语言），不硬编码中文也不硬编码英文（决策点见 §4、细则见 §12.1-8 / §12.2-9） |

## 2. 使用时机

- 用户要系统学习一个新的 AI 项目——类型不限：应用（文本/RAG/Agent/多模态/生成）/ 模型训练 / 平台基建 / 质量保障全覆盖（主流类型索引见 §5.3，未命中类型同样适用）；
- 用户要为某个项目生成「章节化学习计划文档」，要求版式统一、内容贴合项目实际；
- 用户推进学习时，要求文档记录的状态与实际代码产物保持一致；
- 技能被复制到另一个项目/仓库后，可为那个项目独立生成新的学习计划（互不污染）。

## 3. 工作流总览（S0–S5）

| 阶段 | 动作 | 产出物 |
|---|---|---|
| S0 画像 | 探测/询问项目：类型、规模、技术栈、所处阶段、学习目标、交付形态、环境约束 | 画像摘要（写入 LEARN.md 文档身份头） |
| S1 推导 | 从第一性原理拆解"必须走通的环" → 折叠成章节地图 | 章节清单（章数与主题不定，附推导理由） |
| S2 渲染 | 按 §6 模板规范渲染学习计划文档 **LEARN.md**（放目标项目根目录） | LEARN.md |
| — 评审门 | **用户审阅 LEARN.md 并确认**（生成任何代码前必须过，见 §7） | 用户反馈 → 修订 → 确认稿 |
| S3 环境 | 按 LEARN.md 环境章就位（依赖/服务/配置），红线见 §13；**最强手动章**：起服务/装依赖由用户亲手完成（§16） | 可运行环境（环境章产物 verified） |
| S4 逐章循环 | 每章：对齐 → 生成/讲解 → 用户手动点 → 本地绿条验证 → 状态同步 → 收尾（见 §9/§16） | 各章产物 + 手动点完成记录 + 账本推进 + 状态卡更新 |
| S5 验收 | 按 LEARN.md 收官章标准验收（测试/自检/文档一致/盲测复现，§16.4） | 学习完成标记（sync_event 留痕） |

全程铁律：**评审门前不写代码；每章产物必须先绿条后同步；文档状态永远以账本为准。**

## 4. S0 项目画像（先探后问，不猜）

必须拿到以下维度；信息不足时**先探测项目目录与已有文档**，探测仍缺的**逐项向用户提问**，不得臆测：

| 维度 | 要弄清的问题 | 为什么影响设计 |
|---|---|---|
| 类型 | 属 §5.3 哪一层（应用/模型/平台/质量）哪一类？表中未命中的新形态也如实写。被测对象黑盒还是白盒？ | 决定"环"的种类与顺序 |
| 规模 | 模块数、代码量级；已有文档/测试/CI 等资产 | 决定章数与每章粒度 |
| 技术栈 | 语言、框架、模型来源（本地模型 / 云端 API）、数据库、容器化 | 决定环境章内容与命令 |
| 所处阶段 | 从零搭建？已有骨架补功能？已上线要评测/改造？ | 决定学习重点分布 |
| 学习目标 | 会跑 / 会测 / 会改造 / 会独立交付？最终能独立做什么 | 决定验收标准高度 |
| 交付形态 | 只要学习笔记，还是代码/测试/CI 也要真实产出？ | 决定每章产物类型 |
| 环境约束 | 哪些服务需用户手动启动、模型与数据放哪、哪些目录不可删、网络/代理限制 | 写入 §13 通用红线 |
| 共享要求 | 学习产物/本技能是否对外共享（如 GitHub）？有无敏感信息边界？ | 决定 .engine 是否入库、密钥处理 |
| 产出语言 | 学习对话用什么语言？产物（LEARN.md/文档/代码注释）用什么语言？**默认跟随用户当前使用的语言**（用户说中文就中文、说英文就英文）；产物若面向国际读者共享可显式指定英文 | 决定 LEARN.md 与全部产物的书写语言（细则见 §12.1-8 / §12.2-9） |

产出「画像摘要」写入 LEARN.md 文档身份头（见 §6.1），它是后续所有推导的事实基础。

## 5. S1 第一性原理推导 → 动态章节地图（核心，禁止套模板）

**规则：章节数量、主题、顺序由画像决定，本技能不预设任何固定章数，也不复制任何其他项目的章序。**

推导方法是"环"思维：问自己——要真正理解并学会这个系统、从零到能独立改动它，**必须依次走通哪些闭环**？每走通一个环，学习者就获得一项可验收的能力。

### 5.1 推导问题清单（按项目类型取舍）

1. 系统的输入输出边界是什么？它调用哪些外部依赖（模型/库/服务）？
2. 数据从哪来、长什么样、怎么进系统（采集/入库/切分/清洗/格式转换）？
3. 核心处理逻辑分几段（检索/生成/推理/规划/工具调用…）？每段最关键的 1–2 个对象是什么？
4. 怎么验证"做对了"（确定性断言 / 评测指标 / 人工判据 / 门禁）？
5. 运行起来要不要观测（trace / 日志 / 看板 / 成本）？出问题怎么定位？
6. 要不要防护（输入输出过滤 / 安全测试 / 权限 / 合规）？要不要性能与成本考量？
7. 怎么交付（部署 / 打包 / CI / 文档收尾）？收官验收标准是什么？

### 5.2 折叠成章的规则

| 情形 | 折叠策略 |
|---|---|
| 一个环很大（如"数据"含采集+清洗+入库） | 拆成多章，每章一个可验收的子环 |
| 相邻环都很小（如"提示词"+"输出契约"） | 合并为一章 |
| 纯概念环（总览/方法论） | 独立成"无代码章"，只讲目标与概念 |
| 环境/部署类环 | 分别放最前（S3 环境）与最后（交付） |

每章控制在一个学习会话可完成的体量；一章太大就拆，一章太小就并——**章粒度由内容决定，不由模板决定**。

### 5.3 启发式起点（分层索引，仅为参考，禁止照抄）

所有 AI 项目共享基础骨架「环境 → 主线 → 评测 → 部署/收官」；下表只列**各主流类型区别于他类的核心环**，用于提示推导方向，**不是默认模板**。真实章节必须回到 5.1 问题清单按本项目回答；**表中未列出的类型（含新形态）同样走 5.1/5.2 流程——方法有效性不依赖命中本表**。

| 层 | 主流项目类型 | 区别于他类的核心环（基础骨架之上的独有环节） |
|---|---|---|
| 应用层 | LLM 文本应用（问答/摘要/翻译/写作） | 提示词与输出契约 → 评测集 → 回归 → 上线监控 |
| 应用层 | RAG 知识库问答（含 GraphRAG 等变体） | 文档/数据准备 → 检索适配（切分/嵌入/召回/重排）→ 检索质量与生成质量分开评测 → 门禁 |
| 应用层 | Agent（工具调用/多步规划） | 工具定义 → 规划循环 → 记忆/上下文 → 护栏 → 成功率与成本评测 |
| 应用层 | CV 应用（分类/检测/分割/OCR） | 数据与标注 → 模型/API 选型 → 视觉指标评测（mAP/准确率）→ 推理部署 |
| 应用层 | 语音应用（ASR/TTS/实时语音对话） | 音频链路 → 服务/模型 → 语音指标评测（WER/延迟/MOS）→ 实时性验证 |
| 应用层 | 多模态应用（图文/视频理解） | 多模态输入管线 → 上下文窗口与图像分辨率取舍 → 跨模态一致性评测 |
| 应用层 | AIGC 生成工具（文生图/视频/3D/音乐） | 生成管线（基础模型 + 放大/后处理）→ 主观偏好与一致性评测 → 内容安全护栏 |
| 应用层 | 推荐系统 | 特征 → 召回 → 排序 → 离线/在线指标与 A/B → 实时链路 |
| 模型层 | 传统 ML 与 NLP 流水线（分类/回归/NER/情感） | 数据探索 → 特征工程 → 训练 → 评估 → 服务化 → 监控 |
| 模型层 | LLM 微调与对齐训练（LoRA/全参/DPO/RLHF/蒸馏） | 训练数据 → 微调 → 对齐 → 评测回归（防灾难性遗忘）→ 部署比对 |
| 模型层 | AI 数据工程（采集/清洗/标注/质检） | 数据源 → 清洗/去重 → 标注/质检 → 版本与血缘管理 |
| 平台层 | 模型推理/服务平台（部署/量化/加速） | 模型加载与批处理 → 并发/延迟/吞吐 → 弹性与监控 |
| 平台层 | AI 网关与可观测平台（多模型路由/追踪） | 路由与降级 → 限流/熔断 → 调用追踪与计费 |
| 平台层 | 低代码 AI 应用平台（编排/知识库/插件） | 平台功能面走查 → 编排链路（知识库/插件）→ 端到端效果评测 |
| 质量层 | AI 测试与评测工程（横切以上各层） | 被测系统 → 测试资产（考卷/基线）→ 确定性门禁 → 评测报告 → 可观测 → 安全/红队 → 自检收官 |

### 5.4 防复制检查（推导后必做）

自问三连，任一不过即修订：
1. 这些章节是照某个项目抄的，还是由本项目的环推导出来的？——若说不出"为什么必须有这章"，删。
2. 是否存在"为套模板而设"的章（别的项目有、本项目没有对应环）？——删。
3. 是否存在"本项目有、章节却漏了"的环？——补。

推导结果须向用户**口头说清"为什么是这些章、为什么这个顺序"**，评审门确认后才能渲染。

## 6. S2 学习计划文档模板规范（锁外形与写法，不锁内容）

LEARN.md 生成在**目标项目根目录**（与源码同层，随项目走）。版式遵循本规范；若用户有既有手册，可声明"版式对齐该手册"，但**章节内容仍由 S1 推导**。

### 6.1 文档身份头（LEARN.md 顶部）

| 字段 | 内容 |
|---|---|
| 文档标题 | `# <项目名> 学习手册` |
| 定位说明 | 3 行以内：为什么学、学完能做什么、与项目目录的关系 |
| 画像摘要 | S0 画像摘要（维度见 §4：类型/规模/技术栈/阶段/目标/交付形态/环境约束/共享要求/产出语言） |
| 语言 | 本手册正文语言（S0 确认：默认跟随用户对话语言；中文/English 等，不硬编码） |
| 进度总表 | 章 → 状态 的表格（**投影**，以 `.engine/state.json` 为准） |
| 文档约定 | 状态卡语法说明 + 指向本技能（可选） |
| 阅读导航 | 本文档怎么用：各章目的与前置依赖、必读/可跳章建议、产物与手动点分布（人和 Agent 复用/维护本文档的入口） |

### 6.2 版式约定

1. 标题层级：`#` 文档标题；`##` 章（`第 X 章 …`）；`###` 小节（`X.Y`）。
2. 关键函数节统一格式：`#### 📄 源文件 <路径>` 按文件分组 → 同文件/同类函数归组并标注类名；模块级函数注明"不隶属任何类"。函数签名表：入参标 `参数名: 类型`，出参标类型与结构（如 `tuple[float, list[str], list[str]]` = (覆盖率, 命中, 缺失)）。
3. 表格是主体表达方式（文件清单、对比、签名、步骤表）；长段落压缩成表，表格放不下再上短段落。
4. 代码块配详细大白话注释（语言跟随 S0 确认的产物语言：中文场景=中文大白话、英文场景=简单英文，见 §12.1-8）；外部 API/方法调用注释贴调用行末。
5. 每章收尾固定两段：「**本章完成目标**」（验收导向，含实测命令与绿条标准）+「**下一章目标**」（一句话预告 + 一句"为什么下一章讲它"的因果衔接，让章节逻辑连续）。文档末章为「收官验收」章。
6. 文档精简红线：只留重点工程知识与产出物说明（对话式排错/"为什么"往返不进文档，细则见 §12.2-3）。
7. 状态卡语法（人读机读双用）：`> **[st:<id>]** ✅ 已落地（verified）· 绑定：<相对路径>`；枚举见 §11.1。
8. 相对路径引用项目内文件；引用了不存在的路径，评审门前必须修掉。
9. 内容零冗余红线：不得出现「XX版」字样、同一内容只写一遍、括号只放重点备注、拒绝废话冗余（完整细则见 §12.2-7，此处不展开）。

### 6.3 章骨架（默认必备元素集，可经评审门增删）

| 元素 | 作用 |
|---|---|
| X.1 本节目标 | 学完能做什么（验收导向） |
| X.2 文件清单 → 作用 | 本章**交付产物**逐项说明（源文件/配置/测试）；临时与中间文件不列入（见 §9.1） |
| X.3 关键函数/对象 | 按 §6.2 第 2 条分源文件标注类与签名 |
| X.4 执行流程 | 数据怎么流、谁调谁、怎么验证 |
| X.5 测试详解 | 覆盖什么、怎么跑、绿条标准 |
| X.6 手动练习 | 本章必须由用户亲手完成的操作清单（起服务/装依赖/执行核心命令/验证结果/口头复述），Agent 只提供确切命令与判读标准（见 §16） |

> 章内小节同样不固定：纯概念/无代码章可声明去掉 X.2/X.3，只留目标 + 概念 + 练习；某章有特殊主题（如"环境搭建"）可加专属小节——增删都在评审门向用户声明。去掉 X.2/X.3 的章，X.6 仍以「口头复述」形式保留（动手练习是学习的一部分，概念章也不例外）。

## 9. S4 逐章学习循环（每章固定节奏，不得跳步）

| 步骤 | 动作 | 验收要点 |
|---|---|---|
| 1 对齐 | 讲清本章目标与工程取舍，等用户确认再动手 | 用户确认后才进入生成（用户习惯先讨论后编码） |

| 3 验证 | 双轨验证：① Agent 先本地实测绿条自证（跑测试/最小调用，类型零错误为阻断项）；② 其中最能练能力的命令作为「手动点」交给用户亲手执行，输出与 Agent 自证对照一致才通过 | 两组实测输出都贴给用户看，并讲清"哪一行 log 算绿条" |

### 9.1 产物干净：临时文件识别与清理（每章收尾必做，S5 复检）

只有「学习者要保留/复用/验收的交付物」才是产物——进账本、进 LEARN.md 文件清单；其余都是临时文件：**用毕即清、不进账本、不进文档**。

| 临时文件类型 | 示例 |
|---|---|
| 中间转换产物 | 抽取/转换脚本的中间输出（临时 json/csv、未入库的转换件） |
| 调试残留 | 调试 print 输出文件、临时 log、注释掉的代码块、未使用的 import |

| 备份与草稿 | 一次性备份副本、探索脚本、废弃脚手架文件 |

收尾流程（与状态同步同点执行）：
① 对照本章 X.2 文件清单盘点目录，标出清单外新增文件；
② 逐项判定：交付产物 → 补入 X.2 清单与账本；临时文件 → 列入清理清单；

④ S5 收官做全项目复检：目标项目目录只应剩 LEARN.md 清单产物 + `.engine/` + 环境必要目录。

- 若产物要共享（如放 GitHub），执行 §14 共享检查。

## 11. 状态账本与双向同步

### 11.1 状态枚举（唯一合法值）

| code | 含义 | 允许进入的来源 |
|---|---|---|
| `planned` | 文档已规划，产物未生成 | —（初始态） |
| `in_progress` | 正在学习/生成中 | planned |
| `verified` | 产物已生成且实测绿条 | in_progress、dirty |
| `dirty` | 产物被改动但未重新验证（sha256 漂移自动降级） | verified |
| `blocked` | 被环境/依赖阻塞，需人工介入 | 任意 |

状态迁移合法性：`planned → in_progress → verified`；`verified → dirty`（自动）；`dirty → verified`（需重新实测绿条）；`blocked` 从任意态进入（人工介入）、解除后回到实际状态。**不存在 verified 与 dirty 之间的手动互转之外的捷径。**

### 11.2 账本文件 `.engine/state.json`（运行时自动生成）

技能应用到目标项目后，在**目标项目根目录**自动创建 `.engine/` 目录并维护 `state.json`。**技能文件本身不预置、不携带任何账本示例**——账本属于具体目标项目，与技能分离。

只存事实，可派生字段不落库；checksum 用 sha256 前 12 位：

```json
{
  "profile": { "type": "rag", "tech_stack": ["python", "vectordb"], "stage": "from-scratch" },
  "chapters": [
    { "id": "ch1", "title": "环境与脚手架", "kind": "code", "elements": ["files", "functions", "flow", "tests"] }
  ],
  "artifacts": [
    { "id": "art-1", "path": "src/client.py", "sha256": "a1b2c3d4e5f6", "status": "verified", "owned_by": "ch1" }
  ],
  "manual_marks": [
    { "id": "ch2", "status": "verified", "by": "user-confirm", "ts": "2026-09-02T23:40:00" }
  ],
  "sync_events": [
    { "ts": "2026-09-02T23:40:00", "kind": "push", "action": "mark art-1 verified" }
  ]
}
```

字段定义：

| 字段 | 说明 |
|---|---|
| `profile` | S0 画像摘要（type/tech_stack/stage…），仅存档供追溯 |
| `chapters[]` | 章定义：id、title、kind（`code`=有产物 / `concept`=无代码讲解章）、elements |
| `artifacts[]` | 产物登记：path（相对目标项目根）、sha256、status、owned_by（所属章 id） |
| `manual_marks[]` | 人工确认记录（concept 章完成 = 用户在对话中确认，见 11.3） |
| `sync_events[]` | 同步操作审计日志：ts、kind（validate/push/pull/manual_mark/backup/conflict）、action |

**章状态不落库，而是派生**（避免账本内部两份状态打架）：

| 章类型 | 派生规则 |
|---|---|
| code 章 | 聚合其全部 artifacts：全 verified → verified；任一 dirty → dirty；任一 blocked → blocked；存在 planned/in_progress → 取最差未完成态 |
| concept 章 | 无 artifacts → 以 `manual_marks` 中最近一次用户确认记录为准（无记录 = planned） |

账本只登记交付产物（供验收/复用），临时与中间文件不登记、其清理只留 sync_event（§9.1）。账本只增改、不静默删；重要动作写入 `sync_events` 可审计。`.engine/` 是否入库（git）由用户决定：无敏感信息时建议入库（学习进度可随仓库共享）；含密钥/隐私则加入 .gitignore。

### 11.3 双向同步规则

**方向 A（产物改 → 文档同步）**：每次生成/修改代码或环境后，在动作收尾点显式执行——① 重算该 artifact 的 sha256；② 与账本登记值比对，不一致 → 状态降为 `dirty`；③ 重新实测绿条通过 → 回 `verified`；④ 同步 LEARN.md 状态卡与进度总表。**文档里出现的行为（如"已完成某能力"）没有产物绿条支撑时，禁止标 verified。**

**方向 B（文档状态改 → 产物动作）**：用户在文档/评审中把某章标记为"要学/已计划/加内容" → Agent 解析变更生成动作清单：待创建产物 → `planned`；planned 章 → 排入学习；concept 章完成确认 → 记 `manual_mark`。**文档声明超前于产物时，只生成"行动单"，不直接标 verified。**

**触发时机**（无后台监听，全部显式触发）：

| 时机 | 动作 |
|---|---|
| 每个动作收尾点 | 生成完代码 / 跑完测试 / 改完文档结构后，立即执行方向 A 或 B 同步 |
| 每次会话开始 | 执行 `validate`（见下） |
| 用户主动要求 | 全量 validate + 重建文档投影 |

**会话启动 validate 流程**：① 读 state.json，校验 JSON 合法性与枚举合法性；② 遍历全部 artifacts 重算 sha256，漂移者降 `dirty`；③ 比对 LEARN.md 状态卡/进度总表与账本，列出不一致项；④ 汇总输出 dirty/blocked 清单与建议动作；⑤ 全过程写 sync_events。

### 11.4 冲突处理（裁决优先级，永不自动覆盖）

| 冲突 | 处理 |
|---|---|
| C1 文档与账本都改了 | 以账本为事实重建文档投影；两处差异先备份留证，再向用户说明差异 |
| C2 文档声明状态超前（如标 verified 但产物缺失） | 生成行动单补齐产物；补齐前状态按实际（缺产物 = planned） |
| C3 产物被改但未验证 | sha256 漂移 → 自动 `verified → dirty`；人工重新确认绿条后才可回 verified |

裁决优先级：**实测绿条 > 人工明确标记 > 引擎推断**；引擎永不自动覆盖前两者。

### 11.5 一致性保证

① 单一事实源（账本，文档只是投影）；② 写前备份、写后自检（表格列数、状态卡语法、路径存在性、JSON 合法性）；③ 幂等可审计（重复同步无副作用，sync_events 留痕）；④ 会话启动 validate 兜底。

## 12. 代码与文档产出规范（学习者视角的交付标准）

### 12.1 代码产出要求（精简 + 注释，逐条执行）

**代码精简（先于注释）**：只写达成本章目标所需的最小代码——优先标准库与项目既有工具；不提前抽象、不造用不到的封装与"未来可能用"的参数；一个函数只做一件事；不留死代码、注释掉的代码块与调试残留（交付前清掉调试 print/log）；命名即文档，注释只解释"为什么"，不逐行翻译语法。注释要求见下表：

| # | 要求 | 示例 |
|---|---|---|
| 1 | **外部 API / 方法 / 第三方库调用：注释必须贴在该调用行末**，说明"调什么、传什么、拿什么"，不集中堆到文件末尾 | `resp = client.chat(messages)` `# 调远程对话接口：传历史消息，拿模型回复` |
| 2 | 每个文件头部 1–3 行注释：文件职责与归属 | `# 适配层：封装对被测服务的 HTTP 调用，供上层统一使用` |
| 3 | 每个类/函数定义上方：作用 + 入参 + 出参（语言跟随产物，参数名与代码一致；示例为中文场景） | `# 计算覆盖率：入参 answer(str)、expected_keywords(list)；出参 (rate, hit, missing)` |
| 4 | 代码块内按逻辑段配**大白话注释**（语言跟随产物）：解释"为什么这么做 + 心智模型"，不逐行复述语法 | `# 先归一化再比较：模型输出可能带标点/空格，直接比较必失配` |
| 5 | 非显然逻辑（正则、位运算、异步、状态机、算法、魔法值）分步注释 | `# 前 12 位即可唯一标识，太长徒增噪音` |
| 6 | 配置/清单文件（env、yaml、toml、docker、依赖清单）的每个键配行尾或行上注释 | `# 写入模式：dual=双写兼容旧版；新装环境可去掉此行` |
| 7 | 禁止无意义注释（`x += 1  # x 加一`）；禁止整段复制官方文档注释 | 代码本身自明的部分不注释 |
| 8 | **注释语言跟随 S0 确认的产物语言，不硬编码**：中文场景用中文大白话、避免术语堆砌与英文缩写；英文场景用简单英文（plain English）；专有名词（API/命令/库名）保留原文不翻译；概念难懂时给类比。本表示例均为中文场景，英文场景按同样规则替换 | `# 向量库隔离：每轮测试用独立临时目录，像每次考试用新草稿纸` |

### 12.2 文档写作要求

| # | 要求 |
|---|---|
| 1 | 表格为主体表达（清单/对比/签名/步骤）；段落只写表格装不下的连贯论述 |
| 2 | 每章固定收尾「本章完成目标 & 下一章目标」；文档末章为收官验收 |
| 3 | 只留重点工程知识与产物说明；**对话式排错、"为什么"往返、试错过程一律不进文档** |
| 4 | 工程结论/测试总结在原文处用大白话收口一句（结论要能被零基础复述）；是"同处补写"，不是另起"大白话版" |
| 5 | 同一事实只写一处（避免两处漂移）；文档与账本不一致时以账本为准重建投影 |
| 6 | 讲不清就先按"学习者已有经验 → 类比 → 最小可跑 demo → 真实框架（标注进阶）"的顺序组织 |
| 7 | **内容零版本、零废话红线**：① 文档/文件正文不得出现「XX版」字样（如"大白话版/通俗版/正式版"）——同一内容只写一遍，默认即大白话叙述，禁止把同一内容拆成多"版"并存；② 括号只用于重点备注（为什么、工程取舍、类比、判读要点），禁止用括号贴版本标签或"（如上所述）"类空话；③ 删除一切废话与冗余：不写"下面我们来看""由此可知"等过渡口水，不复述前文或表格已有内容，不贴与主题无关的长引文，段落能并表则并表 |
| 8 | **重点突出、取舍有据、因果连贯**：① 先结论后展开，关键信息（命令/路径/验收标准）加粗或单独成行，与背景介绍分层呈现，读者可直接复用而不必通读全文；② 取舍判据——段内每处内容须支撑读者某个动作（跑命令/判读/验收/维护/排错），答不出"支撑什么"就删，不为凑"完整"扩充背景；③ 新增内容前先查重：与前文重复则并表或删，非必要则不加；④ 章间以「下一章目标」的因果衔接串联（§6.2-5），先讲清"这章为什么接上一章"再进入新主题 |
| 9 | **语言跟随用户（S0 确认，见 §4 产出语言）**：① LEARN.md 及全部文档用确认的产物语言书写——中文/英文均可，**默认跟随用户当前使用的语言，不硬编码单一语言**；② 对话（讲解/答疑/口头复述/盲测引导）始终用用户当前使用的语言，用户中途切换语言即跟随切换；③ 专有名词、命令、报错信息、API/库名保留原文不翻译；④ 同一文档不中英混杂（示例代码块注释按注释规则 §12.1-8） |

### 12.3 交付前自检清单（每次交付产物前过一遍）

- [ ] 代码本地实测绿条（log 输出贴出）？类型检查零错误？
- [ ] 外部 API 调用注释全部贴调用行末？
- [ ] 新文件都有职责头注释；新函数都有作用/入参/出参说明？
- [ ] 文档表格列数一致、无对话式排错残留、本章状态卡已同步？
- [ ] 内容无「XX版」字样、无装饰性括号、无废话冗余（§12.2-7）？
- [ ] 本章 X.6 手动练习清单已明确，且用户已亲手完成并回报输出？
- [ ] 代码最小够用、无死代码与调试残留（print/log 已清理）？
- [ ] 本章临时文件已清理（§9.1），LEARN.md X.2 清单与目录现状一致？

## 13. 通用红线（环境、配置与改动操作；随项目画像补充，以下为跨项目通用项）

1. 需用户手动启动的服务（Docker Desktop、本地模型服务、数据库、消息队列等）**一律由用户手动启动**；未运行时提示用户，绝不自动拉起（自动拉起会导致崩溃）。
2. 模型/数据目录以用户告知为准；同一文件多处副本不重复拉取；项目数据卷/数据目录永不删除。
3. 涉及鉴权与中间件的配置（如写入模式、密钥、代理）以官方文档与本地实测为准（改动操作遵循 §13-7）。
4. 一切路径以目标项目根为基准，文档与账本中只写相对路径；技能文件本身不含任何绝对路径。
5. 密钥/凭据只进 .env（不入库）；.env 永不写入文档与账本；共享前执行 §14 检查。
6. 学习会话中，能练手的操作（拉依赖/起服务/执行关键命令/验证结果）以用户亲手执行为主，Agent 提供确切命令、判读标准并兜底，仅纯事务性动作可代劳（细则见 §16）。
7. 改动前先备份、只改指定处、失败即回退；改动清单用表格列明（路径 + 改动类型），便于回滚核对。

## 14. 跨项目可移植性（零依赖保障与迁移流程）

- **本技能零外部依赖**：不引用任何特定项目的路径、文件名、工具栈或技术商标；唯一会在目标项目内创建的东西是运行时生成的 `.engine/` 账本。
- **应用到一个新项目**的流程：① 确认技能文件位于目标仓库（可放仓库根或 docs/ 下，无强制位置）；② 从 S0 开始对该项目画像（不读取任何旧项目的 LEARN.md 作章节参考）；③ 生成该项目的 LEARN.md 与 `.engine/`。
- **多项目共存**：每个项目各自持有自己的 LEARN.md 与 `.engine/`，互不读写；技能文件可多仓库各放一份。
- **共享检查（如放 GitHub）**：发布前确认技能文件内无绝对路径、无密钥、无任何项目私密信息；目标项目共享时自行检查 .env、数据卷、密钥不入库；是否携带 `.engine/` 进度由用户决定（含敏感信息则忽略它）。

## 16. 用户手动实践规范（学完 = 能独立交付）

学习流水线中 Agent 负责：讲解概念、生成代码与文档、绿条自证、状态同步、兜底排错。**但"学会"的判据不是"Agent 跑通了"，而是"用户自己能跑通"**——因此本技能在每一章都内嵌「手动点」（LEARN.md 每章 X.6）：凡是能练出肌肉记忆的动作，执行权优先移交用户亲手完成；Agent 提供确切命令、参数解释与输出判读标准，用户亲手执行，卡住三次仍无解 Agent 才兜底。绝不因"自动更快"而替用户把操作做完，也绝不因"用户手动慢"而跳过手动点。

### 16.1 手动点分级（三类，按能力价值安排）

| 级别 | 典型动作 | 谁执行 | 为什么 |
|---|---|---|---|
| 必练·绝不代劳 | 守护类/GUI 服务启动（Docker Desktop、本地模型服务、数据库、中间件控制台等）；管理界面/浏览器操作（数据导入、应用发布、配置勾选）；需账号或交互界面的动作 | 用户亲手 | 自动拉起易崩且学不到排障；界面操作无法可靠替代；这是真实工作每天要做的 |
| 强练·首次必亲手 | 拉依赖/装工具（pip install、npm install、docker pull、ollama pull）；执行核心命令（跑测试、最小调用、启动脚本）；解读 log 与结果（绿条在哪一行、失败看哪一段） | 用户执行，Agent 给确切命令并逐参数解释；用户回报输出，Agent 判读 | 建立"输入命令 → 看输出 → 判断成败"的反射，而不是只会复述文档 |
| 弱练·可自动但要能复述 | 重复性验证脚本、批量回归、账本同步、格式检查 | Agent 执行，但用户须能讲清"这命令/脚本干什么、为什么这么写" | 防"看过就会"；Agent 可随时抽查复述 |

> 每章默认安排 1–3 个手动点（以强练级为主），写进 LEARN.md 该章 X.6；选最能练能力的动作，不拿纯事务动作凑数。概念章的手动点 = 口头复述（16.3）。

### 16.2 手动点的执行节奏（嵌进 S4 循环）
1. 进入本章"验证"前，Agent 把 X.6 手动点清单报给用户：动作、确切命令、预期输出（绿条长什么样）、失败先自查什么。
2. 用户亲手执行并回报输出；Agent 判读，并与其自身的绿条自证结果对照；不一致时先让用户自查三步（读报错首行 → 看它指向哪个文件/哪一行 → 对照预期输出找差异），仍卡住 Agent 才介入。
3. 手动点全部完成、输出一致，本章才能进入"同步与收尾"（§9 步骤 4/5）。

### 16.3 每章口头复述（只发生在对话框，不进文档）
每章收尾，用户不看 LEARN.md 的命令与状态卡，口头回答三问，Agent 纠正补漏：
1. 本章跑通了什么？关键命令是什么、绿条长什么样？
2. 本章最关键的概念/工程取舍，用自己的话讲一遍（能给外行讲清更好）；
3. 本章卡在哪、怎么解决的？
> 复述与排错过程只留在对话框（对齐 §12.2-3 文档精简红线），不许把复述稿写进文档。

### 16.4 收官盲测（终极手动验收，S5 硬性一项）
1. 用户只看 LEARN.md 的功能目标，隐藏全部命令、代码与状态卡；
2. 从环境启动开始，独立把项目最小链路完整跑通：起服务 → 装依赖 → 执行 → 验证绿条；
3. Agent 全程只观察与提问引导（"下一步做什么？为什么？"），不代劳、不直接给答案；
4. 失败时用户先按自查三步独立排错，三次尝试仍卡住 Agent 才介入；
5. 跑通后写 sync_event（记 manual_mark：盲测通过），列入收官验收。
盲测通过是"学完 = 能独立交付"的最终证据；未过则回到对应章节补手动点，不进收官总结。

## 17. 完成标准（怎么算这套技能用到位）

- **新项目**：收到一份 LEARN.md——章数与主题由该项目的环推导（能逐章说出"为什么有这章"），版式与写作规范符合 §6/§12，评审门通过。
- **逐章推进**：每章产物绿条自证；`.engine/state.json` 与 LEARN.md 状态卡一致；不存在 `verified` 而无绿条支撑的条目；sync_events 全程留痕。
- **手动能力**：每章手动点用户亲手完成、口头复述过关；收官盲测通过——用户能独立从环境启动跑通最小链路（§16.4）。
- **内容品质**：LEARN.md 与全部产物无「XX版」字样、无装饰性括号、无废话冗余（§12.2-7）。
- **语言一致**：对话与全部产物（文档/注释）的语言与 S0 确认一致，全程无硬编码单一语言的痕迹（§12.2-9）。
- **产物整洁**：目标项目目录无临时/调试/缓存残留，只含 LEARN.md 清单产物与 `.engine/`；每章收尾与收官均做过干净检查（§9.1）。
- **收官**：LEARN.md 收官章验收标准全部达成；会话结束能输出"该项目学会了什么、用户能独立复现到什么程度、遗留 blocked 项、下一步建议"。
- **可移植**：技能文件可被复制到任意新项目/仓库，独立为新项目生成学习计划，不残留前一个项目的任何痕迹。
